# Discourse Endpoints

Android v1 uses standard Discourse JSON endpoints and homepage bootstrap HTML.

- `GET /latest.json?page={page}` - latest topic feed with optional `topic_list.more_topics_url`
- `GET /new.json?page={page}` - new topic feed with optional `topic_list.more_topics_url`
- `GET /top.json?page={page}` - top topic feed with optional `topic_list.more_topics_url`
- `GET /site.json` - site metadata including category definitions for category badge rendering
- `GET /t/{id}.json` - topic detail with `posts_count`, `post_stream.stream`, and optional server-ranked `details.participants` used for immediate composer mention candidates. Authenticated responses also carry `highest_post_number`, `last_read_post_number`, and `last_read_post_id` (the caller's Discourse read position; absent/0 when anonymous).
- `GET /t/{id}/{postNumber}.json` - the same topic detail envelope with the initial `post_stream.posts` window centered around the requested floor. Normal authenticated opens first read `/t/{id}.json` to discover `last_read_post_number`, then keep the skeleton visible while this endpoint loads that window; the UI never renders floor 1 and jumps afterward. Explicit post-number navigation uses this endpoint directly.
- `POST /topics/timings` - report read progress: form fields `topic_id`, `topic_time` (total dwell ms), and `timings[<post_number>]=<ms>` per read post; requires the `X-CSRF-Token` session header. Advancing the server read position makes the next `GET /t/{id}.json` return a larger `last_read_post_number`.
- `GET /t/{id}/posts.json?post_ids[]={id}` - incremental topic post chunk fetch
- `GET /posts/{postId}/replies?after={postNumber}` - direct replies to one post, returned as a JSON post array. The topic-detail reply sheet starts with `after=1`, then advances using the greatest returned `post_number`; the source post's `reply_count` is the authoritative total. Fixture at `fixtures/discourse/post-replies.json`.
- `GET /search.json?q={query}&page={page}` - grouped topic, post, and user search; post hits include `topic_id` and may include `post_number` for native in-topic jumps
- `GET /u/search/users?term={prefix}&topic_id={topicId}&include_groups=true&limit=6` - composer-aware `@mention` autocomplete. Unlike generic search, this endpoint accepts a blank term, ranks candidates in topic context, and returns both users and mentionable groups. Fixture at `fixtures/discourse/mention-users.json`.
- `GET /u/{username}.json` - public profile payload; beyond the core user fields, the profile screen also reads linux.do/Discourse plugin fields `gamification_score`, `cakedate`, `total_followers`, `total_following`, `accepted_answers`, `primary_group_name`, and `last_posted_at`
- `GET /user_actions.json?username={username}&filter={4|5}&offset={offset}&limit=20` - authenticated/public user activity feed used by Profile actions. Filter `4` returns topics created; filter `5` returns replies/posts. Each action may include `post_number`, `post_id`, or an action `id`; the client preserves these as floor navigation and stable row identity so same-topic replies do not collapse even when `post_number` is absent. Pagination advances from the raw server page count, not the filtered display-row count, and ends only on a raw short page.
- `GET /notifications.json?offset={offset}&limit={limit}` - the reader's own in-app notification history, newest first. Each item carries `notification_type`, `read`, `created_at`, `topic_id`, `post_number`, `slug`, `fancy_title`, a `data` object, and - for the types that have an actor - `acting_user_name` and `acting_user_avatar_template` (a `{size}` template). `user_id` is the *recipient*, never the actor: the actor is `data.display_username`, falling back to `data.original_username` and `data.username`, and the topic's title is `fancy_title`, falling back to `data.topic_title`. A notification about a post is opened at its own `post_number`; the types with no topic (`granted_badge`, the consolidated likes and links, `invitee_accepted`, chat) carry none, so a client has to draw them without a destination. `total_rows_notifications` is the count before `offset`/`limit`, so paging advances by the page's own row count and ends when it reaches that total. `fixtures/discourse/notifications.json`.
- `GET /session/current.json` - preferred current-user identity lookup during session restore
- `GET /session/csrf` - preferred CSRF token refresh for authenticated writes; bootstrap HTML still provides a fallback hint during session restore
- `POST /posts.json` - authenticated topic reply/create post with form fields `topic_id`, `raw`, optional `reply_to_post_number`, and `X-CSRF-Token`
- `POST /uploads.json` - authenticated media upload as the web composer sends it: `multipart/form-data` with the file part named `file`, `upload_type=composer`, `synchronous=true` (so the answer carries the id and URL instead of the asynchronous upload's empty acknowledgement), and `X-CSRF-Token`. The answer's `url` is what a post embeds (absolute, or a path to resolve against the base URL) plus `original_filename`, `width`, `height`, `extension`, `short_url` and `human_filesize`; fixture at `fixtures/discourse/upload-response.json`. `width` and `height` are **null** for anything that is not an image or a video (a `.zip`, a `.pdf`), so a client that reads them must treat them as optional - a non-nullable number there fails the decode of a good 200 response. What the client inserts for the upload is the site's own markdown, chosen by the *file's* kind the way the server chooses it (`FileHelper.is_supported_image?`) and pointed at the answer's `short_url`, which is what the site's own composer inserts: an image or video becomes `![name|WxH](upload://xxx.png)` (`|WxH` from the answer's `width` and `height`, and dropped when either is missing or zero, which is what the site does for a file whose dimensions it could not read), anything else becomes `[name|attachment](upload://xxx.zip) (12.3 KB)`. The lowercase `|attachment` marker is what makes the cook emit `<a class="attachment" href="...">name</a>` (the marker is read from the link's label, and the size text is cosmetic, supplied from `human_filesize`), and the cook resolves `upload://` to the upload's own URL on the server. A site that answers without a `short_url` falls back to the answer's `url`, resolved against the base URL, which cooks to the same link; fixtures at `fixtures/discourse/upload-response.json` (image) and `fixtures/discourse/upload-response-attachment.json` (a file the site will not render inline).
- `POST /bookmarks.json` - authenticated post bookmark create with form fields `bookmarkable_id`, `bookmarkable_type=Post`, `auto_delete_preference`, and `X-CSRF-Token`
- `DELETE /posts/{id}/bookmark` - authenticated post bookmark removal with `X-CSRF-Token`
- `PUT /polls/vote` - authenticated poll vote with form fields `post_id`, `poll_name`, `options[]`, and `X-CSRF-Token`; the discourse-poll engine registers this route as `PUT` (not `POST`). `options[]` carries the option **digest** (`polls[].options[].id`), not the option's position or its HTML; a `ranked_choice` poll sends `options[0][digest]=<digest>` with `options[0][rank]=<n>` per ranked option. Response body is `{ "poll": {...}, "vote": ["<option_id>", ...] }` with the updated poll and the current user's normalized selection (`{digest, rank}` objects for `ranked_choice`). The poll inside a vote response is the only place `options[]` carries `chosen` (and, for ranked polls, `rank`), so a client that keeps its poll data up to date from this response does not have to re-read the topic to know what it voted for. Fixture at `fixtures/discourse/poll-vote-response.json`.
- `DELETE /polls/vote` - authenticated poll vote retraction with form fields `post_id`, `poll_name`, and `X-CSRF-Token`; allowed when the poll is open, the topic/post is still active, the user can post in the topic, and (if configured) the user belongs to the poll’s allowed groups. Discourse web UI also retracts on single-choice re-tap of the selected option. Its response body is `{ "poll": {...} }` with no `vote` key (the reader's selection is gone by definition).
- `GET /polls/voters.json?post_id={id}&poll_name={name}&option_id={option}&page={page}&limit={limit}` - public poll voter list. `option_id` is optional; pagination is independently partitioned per option, `page` starts at 1, and `limit` is clamped to 1..50. The response has no total/has-more field and omits an option key on an exhausted page, so the client uses the poll option's own vote count and page size to determine completion. Regular/multiple/ranked polls return an option map; number polls return a flat array and require a separate DTO path before native voter-list support. Fixture at `fixtures/discourse/poll-voters.json`.
- `GET /discourse-reactions/posts/{id}/reactions-users.json` - public reaction-user groups. Optional `reaction_value={id}` limits the response to one reaction. The current discourse-reactions controller does not support `offset`, `limit`, or a cursor and caps each returned group to its most recent 27 users while preserving the group-wide `count`; fixture at `fixtures/discourse/reaction-users.json`. Clients must not present the returned `users` array as a complete list when `count > users.size`.
- `GET /` - homepage HTML used for bootstrap parsing and WebView fallback
