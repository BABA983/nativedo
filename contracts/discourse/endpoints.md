# Discourse Endpoints

Android v1 uses standard Discourse JSON endpoints and homepage bootstrap HTML.

- `GET /latest.json?page={page}` - latest topic feed with optional `topic_list.more_topics_url`. Each topic carries the caller's own read state for it: `unread_posts` (and `unseen` for a topic that was never opened) is what the reader has left to read, and it follows `last_read_post_number` - a topic whose position `/topics/timings` has advanced comes back with a smaller count, and a topic that is fully read with `unread_posts: 0`. The count is only carried for a topic the reader is notified about (`notification_level` 2 or higher); a topic without it has none to draw.
- `GET /new.json?page={page}` - new topic feed with optional `topic_list.more_topics_url`
- `GET /top.json?page={page}` - top topic feed with optional `topic_list.more_topics_url`
- `GET /site.json` - site metadata including category definitions for category badge rendering
- `GET /categories.json` - the site's category list behind a topic-list filter: `category_list.categories[]`, the same entries `site.json` embeds (plus `can_create_topic`, `topic_count`, `position`, `description_text`). Each entry carries `id`, `name`, `slug`, `color` and `text_color` (hex without `#`, e.g. `32C3C3`), and a child category appears inside its parent's `subcategory_list` with `parent_category_id` set. The filter strip is built from entries with no `parent_category_id`; `fixtures/discourse/categories.json` records linux.do's own names and colors as the bootstrap carries them. Rows are ordered as the site orders them (`position`). The home screen's search lists the same entries on its 分类 page, narrowed to the query client-side because the site has no category search route.
- `GET /c/{slug}/{id}/l/latest.json?page={page}` - one category's latest feed: the `latest.json` envelope (`topic_list.topics[]`, `users[]`, `topic_list.more_topics_url`) restricted to that category. The route needs both the slug and the id (`/c/develop/4/l/latest.json`); paging re-requests the same route with a higher `page`.
- `GET /tags.json` - the site's tags, for filtering a topic list: `{"tags":[{"id","text","name","slug","description","count","pm_only"}]}` (a site that lists tags by group also answers `extras.tag_groups[].tags`, and a client that only reads `tags` loses nothing because the ungrouped list is always there). `slug` is the URL form of the name - the site substitutes `<id>-tag` for a tag that has none - and each entry carries its id as well, because the canonical tag route takes both. `count` is how many topics carry the tag. Fixture at `fixtures/discourse/tags.json`. The home screen's search lists the same entries on its 标签 page, narrowed to the query client-side, and a chosen tag filters the list through the tag routes below.
- `GET /tag/{slug}/l/latest.json?page={page}` - one tag's latest feed: the `latest.json` envelope restricted to topics that carry the tag. The tag route also accepts the id (`/tag/{slug}/{id}`), which is what a client holding both uses.
- `GET /tags/c/{category_slug}/{category_id}/{tag_slug}/{tag_id}/l/latest.json?page={page}` - the same feed restricted to one **category and** one tag. This is the canonical combined route (note the `tags/c/` prefix and that the tag's id is part of the path); the two filters combine, so a client that offers both asks this one when both are set. Fixture at `fixtures/discourse/tag-latest.json`.
- `GET /t/{id}.json` - topic detail with `posts_count`, `post_stream.stream`, and optional server-ranked `details.participants` used for immediate composer mention candidates. The topic's own `category_id` and the reader's own topic-level bookmark (`bookmarked`, `details.created_by` naming the original poster with `username`/`name`/`avatar_template`) are read for the header's center capsule; the category's name comes from the cached `/categories.json` list. Authenticated responses also carry `highest_post_number`, `last_read_post_number`, and `last_read_post_id` (the caller's Discourse read position; absent/0 when anonymous).
- `GET /t/{id}/{postNumber}.json` - the same topic detail envelope with the initial `post_stream.posts` window centered around the requested floor. Normal authenticated opens first read `/t/{id}.json` to discover `last_read_post_number`, then keep the skeleton visible while this endpoint loads that window; the UI never renders floor 1 and jumps afterward. Explicit post-number navigation uses this endpoint directly.
- `POST /topics/timings` - report read progress: form fields `topic_id`, `topic_time` (dwell ms since the last report), and `timings[<post_number>]=<ms>` per floor the reader was on (also ms since the last report; numbers below 1 and above `highest_post_number` are dropped). The server **adds** what it is sent to the per-floor row, so the values are deltas, and it advances the reader's `last_read_post_number` to the highest floor the report names (what a topic list's unread counts are made of). It clamps each floor and `topic_time` to 60 000 in one request. Requires the `X-CSRF-Token` session header. Time is the reader's real reading time, counted the way Discourse's own screen-track counts it: only while the app is in front, the floor is in the viewport, and the reader has scrolled within the last three minutes; a client keeps counting only up to six minutes per floor per visit.
- `GET /t/{id}/posts.json?post_ids[]={id}` - incremental topic post chunk fetch
- `GET /posts/{postId}/replies?after={postNumber}` - direct replies to one post, returned as a JSON post array. The topic-detail reply sheet starts with `after=1`, then advances using the greatest returned `post_number`; the source post's `reply_count` is the authoritative total. Fixture at `fixtures/discourse/post-replies.json`.
- `GET /search.json?q={query}&page={page}&type_filter={topic|posts|users}` - grouped search. One answer carries all three lists: `topics[]` (the same topic fields a feed carries), `posts[]` (each with `topic_id`, `post_number`, `topic_title`, `blurb` and the poster's `username`/`avatar_template` - what a post hit needs to open its topic at that floor), and `users[]` (`username`, `name`, `avatar_template`). `grouped_search_result` reports `more_topics`, `more_posts` and `more_full_page_results`, which is how a client knows the answer was cut short. `type_filter` is optional and narrows the same route to one kind. Fixture at `fixtures/discourse/search.json`. The home screen's search reads all three fields from one request and keeps them on their own tabs.
- `GET /u/search/users?term={prefix}&topic_id={topicId}&include_groups=true&limit=6` - composer-aware `@mention` autocomplete. Unlike generic search, this endpoint accepts a blank term, ranks candidates in topic context, and returns both users and mentionable groups. Fixture at `fixtures/discourse/mention-users.json`.
- `GET /u/{username}.json` - public profile payload; beyond the core user fields, the profile screen also reads linux.do/Discourse plugin fields `gamification_score`, `cakedate`, `total_followers`, `total_following`, `accepted_answers`, `primary_group_name`, and `last_posted_at`
- `GET /user_actions.json?username={username}&filter={4|5}&offset={offset}&limit=20` - authenticated/public user activity feed used by Profile actions. Filter `4` returns topics created; filter `5` returns replies/posts. Each action may include `post_number`, `post_id`, or an action `id`; the client preserves these as floor navigation and stable row identity so same-topic replies do not collapse even when `post_number` is absent. Pagination advances from the raw server page count, not the filtered display-row count, and ends only on a raw short page.
- `GET /notifications.json?offset={offset}&limit={limit}` - the reader's own in-app notification history, newest first. Each item carries `notification_type`, `read`, `created_at`, `topic_id`, `post_number`, `slug`, `fancy_title`, a `data` object, and - for the types that have an actor - `acting_user_name` and `acting_user_avatar_template` (a `{size}` template). `user_id` is the *recipient*, never the actor: the actor is `data.display_username`, falling back to `data.original_username` and `data.username`, and the topic's title is `fancy_title`, falling back to `data.topic_title`. A notification about a post is opened at its own `post_number`; the types with no topic (`granted_badge`, the consolidated likes and links, `invitee_accepted`, chat) carry none, so a client has to draw them without a destination. `total_rows_notifications` is the count before `offset`/`limit`, so paging advances by the page's own row count and ends when it reaches that total. `fixtures/discourse/notifications.json`.
- `POST /message-bus/{clientId}/poll` - Discourse's live channel endpoint (the `message_bus` gem); it is the only push-like source, and the site's own web client long-polls it. The body is a form (`application/x-www-form-urlencoded`) whose field names are channel names and whose values are the channel-local id of the last message this client received there (`/latest=41&/new=7&__seq=2`), plus `__seq`, an integer that increments on every request (the server abandons a request with the same client id and a lower sequence). An id of `-1` means "no backlog, only messages published from now on" (and is also what the server stores for an id the channel never reached); `0` asks for the whole backlog, `-2` for the last message plus what follows. The client id is opaque and per-session - the web client generates 32 random hex characters - and changing it abandons the old subscriptions. The answer is a JSON array of message objects `{"global_id": <int>, "message_id": <int>, "channel": "...", "data": <channel payload>}`; `message_id` is the id a client keeps per channel and sends back next time (never `global_id`, which is the bus-wide id and is not what the poll accepts). Long polling holds the request open until a message arrives or the server's interval lapses (25 s by default), so the read timeout must exceed that; `POST .../poll?dlp=t` disables long polling and answers at once (a diagnostic probe). Headers the reference client sends: `X-SILENCE-LOGGER: true`, and `Dont-Chunk: true` when it wants one whole JSON array instead of a stream. Without `Dont-Chunk`, and when the server has chunked encoding enabled, the body is a series of JSON arrays separated by `\r\n|\r\n` (the gem escapes a literal separator inside a frame as `\r\n||\r\n`); a proxy may re-cut the HTTP chunks, so a client must split on that separator, never on transport chunks. A `429` carries `Retry-After` in seconds; the reference client waits out the greater of `Retry-After` and 15 s, and on transport/5xx failures waits a linearly growing multiple of its interval capped at 180 s. The route is Rack middleware: no CSRF token is needed, and the same cookies as the rest of the session must ride the request (`_t`/`_forum_session` decide which user-targeted messages are visible). A challenge, a logout or an outage here is only a failed poll - the poller backs off and must not start a login flow itself. Sources: `discourse/message_bus` README + `lib/message_bus/rack/middleware.rb` + `lib/message_bus/client.rb` (body formats, `dlp`, `Dont-Chunk`, separator, sequence, `/__status`), and `discourse/discourse` `frontend/discourse/app/models/topic-tracking-state.js` + `frontend/discourse/app/instance-initializers/subscribe-user-notifications.js` + `app/models/topic_tracking_state.rb` + `app/models/user.rb` for channels, ids and payloads. Device-observed on linux.do (2026-10-05, emulator + a physical phone): the site's own origin answers this route with a Cloudflare 404 (`server: cloudflare`, a 10-byte plain-text `Not Found.`) - Cloudflare fronts linux.do and does not pass `/message-bus/*` through - while `meta[name=shared_session_key]` and the preloaded `siteSettings.long_polling_base_url` name where the web client actually polls. Polling that base (a different origin) with `X-Shared-Session-Key` answers `200` with one JSON array per request (`Dont-Chunk: true` set; no `Content-Length` or `Transfer-Encoding` header observed on the responses), and the cadence is delivery-driven: while linux.do was busy, completed polls were 0.2-9 s apart, each carrying `/latest` bump messages, with the client's 100 ms floor between deliveries and no 403/429 in the run. The first configuration attempt polled the wrong base and every poll 404'd; the poller backed off 3 s, 6 s, 9 s (no storm) until the base was fixed. On this site the rendered page is a JSON `script#data-preloaded` (not a div attribute) and `topicTrackingStateMeta` named 7 channels; the preloaded `currentUser` carried `id`, `notification_channel_position`, `unread_notifications`, `unread_high_priority_notifications` and `all_unread_notifications_count` (all zero for this reader at the time), so the badge seeds from the page and then follows the channel.
- The message-bus `/__status` message is the poll's id-correction mechanism: `{"global_id": -1, "message_id": -1, "channel": "/__status", "data": {"/latest": 41, "/new": 7}}`. The server sends it immediately for every channel subscribed at `-1`, and whenever a message could not be delivered to this client (it was filtered to other users, or the client's id is ahead of the bus, in which case the client's stored id is reset and the status carries the real one). A client must adopt the values in `data` for the channels it subscribes to, even when that means moving an id backwards; otherwise it keeps asking for a position the channel never had and never receives the next messages.
- Message-bus channels this client uses: `/latest` carries `message_type: "latest"` (`topic_id` plus a `payload` of `bumped_at`, `category_id`, `archetype`, and `tags` when the site reports them) when a topic is bumped, and `muted`/`unmuted` state messages for user-targeted clients; `/new` carries `message_type: "new_topic"` when a topic is created; `/notification/{userId}` carries the reader's unread counts (`unread_notifications`, `unread_high_priority_notifications`, `all_unread_notifications_count`, plus `last_notification`, `recent`, `seen_notification_id`); `/notification-alert/{userId}` carries one per-post alert (`notification_type`, `post_number`, `topic_title`, `topic_id`, `post_id`, `excerpt`, `username`, `post_url`, `group_name`) for system notifications; `/unread/{userId}` carries the user-targeted `unread`/`read`/`dismiss_new`/`dismiss_new_posts` state messages. Channels are user/group targeted at publish time, so a subscribed client only receives what its session may see; the local linux.do client subscribes `/latest`, `/new` and `/notification/{userId}` (alert/unread channels are documented for later).
- The ids a subscription starts from are the site's own, not the client's guess: a rendered Discourse page preloads `topicTrackingStateMeta` (the site's `MessageBus.last_ids` for `/latest`, `/recover`, `/delete`, `/destroy`, `/new`, `/unread`, `/unread/{userId}`) and the `currentUser` object, whose `notification_channel_position` is `MessageBus.last_id("/notification/{userId}")`, synced just before the page is rendered. A client that has them subscribes with them and replays what arrived since the page was built; a client without them starts every channel at `-1` and takes the first `/__status` as its starting point. Only the homepage bootstrap (or a session payload that mirrors it) carries these positions - the topic/journal endpoints do not. linux.do renders the preload as a JSON `script#data-preloaded` element whose text is the object (each value a JSON string containing the object), not the older `<div id="data-preloaded" data-preloaded="...">`; a parser that only knows the div silently gets no ids, no user and no counts, which is why both shapes are read (`fixtures/discourse/home-bootstrap.html` mirrors the script shape linux.do ships). Sources: `lib/application_layout_preloader.rb`, `app/serializers/topic_tracking_state_serializer.rb`, `app/models/user.rb#sync_notification_channel_position` in `discourse/discourse`; `fixtures/discourse/message-bus-poll.json` holds the delivered-message shapes.
- `GET /session/current.json` - preferred current-user identity lookup during session restore; also the read the device-flow probe makes with a `User-Api-Key` header (status + username only)
- `GET /session/csrf` - preferred CSRF token refresh for authenticated writes; bootstrap HTML still provides a fallback hint during session restore
- `POST /user-api-key/device.json`, `POST /user-api-key/device/poll.json`, `POST /user-api-key/revoke` - User API Key device authorization (linux.do: `/login/device`); creates a device grant, polls it, and revokes the resulting key. The grant is approved in a signed-in browser and yields an encrypted User API Key, not a `_t` session. Full contract in `contracts/discourse/device-authorization.md`; shapes in `fixtures/discourse/user-api-key-device.json`.
- `POST /posts.json` - authenticated topic reply/create post with form fields `topic_id`, `raw`, optional `reply_to_post_number`, and `X-CSRF-Token`. With `title` and `category` (a category id) instead of `topic_id` the same route starts a **new topic**: the site creates it with the post as its first floor, and answers with that post (`id`, `post_number` 1, plus the site's own `topic_id`, `topic_slug` and `topic_title`, which a client that only refreshes its list does not need). A title, a category and a non-empty `raw` are all required; the site refuses a missing or rejected one with 422 and the same `errors` array the rest of the API answers a refused write with (`{"errors":["标题过短（最少 15 个字符）"],"error_type":"invalid_parameters"}`, fixture at `fixtures/discourse/error-422-post.json`), and the message in it is what the composer shows the reader - a status line is not something a reader can act on.
- `POST /uploads.json` - authenticated media upload as the web composer sends it: `multipart/form-data` with the file part named `file`, `upload_type=composer`, `synchronous=true` (so the answer carries the id and URL instead of the asynchronous upload's empty acknowledgement), and `X-CSRF-Token`. The answer's `url` is what a post embeds (absolute, or a path to resolve against the base URL) plus `original_filename`, `width`, `height`, `extension`, `short_url` and `human_filesize`; fixture at `fixtures/discourse/upload-response.json`. `width` and `height` are **null** for anything that is not an image or a video (a `.zip`, a `.pdf`), so a client that reads them must treat them as optional - a non-nullable number there fails the decode of a good 200 response. What the client inserts for the upload is the site's own markdown, chosen by the *file's* kind the way the server chooses it (`FileHelper.is_supported_image?`) and pointed at the answer's `short_url`, which is what the site's own composer inserts: an image or video becomes `![name|WxH](upload://xxx.png)` (`|WxH` from the answer's `width` and `height`, and dropped when either is missing or zero, which is what the site does for a file whose dimensions it could not read), anything else becomes `[name|attachment](upload://xxx.zip) (12.3 KB)`. The lowercase `|attachment` marker is what makes the cook emit `<a class="attachment" href="...">name</a>` (the marker is read from the link's label, and the size text is cosmetic, supplied from `human_filesize`), and the cook resolves `upload://` to the upload's own URL on the server. A site that answers without a `short_url` falls back to the answer's `url`, resolved against the base URL, which cooks to the same link; fixtures at `fixtures/discourse/upload-response.json` (image) and `fixtures/discourse/upload-response-attachment.json` (a file the site will not render inline).
- `POST /bookmarks.json` - authenticated post bookmark create with form fields `bookmarkable_id` (the post's id), `bookmarkable_type=Post`, `auto_delete_preference`, and `X-CSRF-Token`. The answer is the site's own acknowledgement - `{"success":"OK","id":<bookmark id>}` and nothing else: the bookmark's fields are not in it, so a client that needs them reads them off the post (below) or re-lists.
- `DELETE /posts/{id}/bookmark` - authenticated post bookmark removal with `X-CSRF-Token`; the answer is `{"success":"OK","topic_bookmarked":false}`.
- `PUT /t/{id}/bookmark.json` - authenticated topic bookmark create (Discourse's `topics#bookmark`), `X-CSRF-Token` only, no body. A topic's bookmark has no single id the client keeps: the topic payload's own `bookmarked` is the state, and the undo is the route below.
- `PUT /t/{id}/remove_bookmarks.json` - authenticated topic bookmark removal (Discourse's `topics#remove_bookmarks`), `X-CSRF-Token` only, no body; drops the reader's bookmarks on the topic.
- `GET /u/{username}/bookmarks.json?page={page}&limit={limit}` - the reader's own bookmarks, newest first (pinned ones first), `page` from 0 and `limit` at most 20. The site answers it for the reader themselves only (`can_see_bookmarks?` is "is me", admins excepted). A page with rows arrives as `user_bookmark_list.bookmarks[]` plus `more_bookmarks_url` when there are more; a page the filtered list has nothing for is a bare `{"bookmarks":[]}` with **no wrapper at all** - and an empty answer carries no `more_bookmarks_url`, so it is the end of the list. A post bookmark carries `id`, `created_at`, `bookmarkable_id` (the post's id), `bookmarkable_type`, `topic_id`, `linked_post_number` (the post's floor in the topic), `title`/`fancy_title`, `excerpt`, `slug`, `highest_post_number` and an embedded `user` (`username`, `name`, `avatar_template`); `deleted`/`hidden` mark rows whose post or topic is gone. Fixture at `fixtures/discourse/user-bookmarks.json`.
- A post's own payload carries the reader's bookmark state: `bookmarked` always, and `bookmark_id`/`bookmark_name`/`bookmark_reminder_at`/`bookmark_auto_delete_preference` when it is true. `bookmarked` is the viewer's own state, so a post the reader has bookmarked says so on the next read of the topic.
- `PUT /polls/vote` - authenticated poll vote with form fields `post_id`, `poll_name`, `options[]`, and `X-CSRF-Token`; the discourse-poll engine registers this route as `PUT` (not `POST`). `options[]` carries the option **digest** (`polls[].options[].id`), not the option's position or its HTML; a `ranked_choice` poll sends `options[0][digest]=<digest>` with `options[0][rank]=<n>` per ranked option. Response body is `{ "poll": {...}, "vote": ["<option_id>", ...] }` with the updated poll and the current user's normalized selection (`{digest, rank}` objects for `ranked_choice`). The `vote` array is where a `regular` poll's answer carries the reader's own selection, so a client that keeps its poll data up to date from this response does not have to re-read the topic to know what it voted for; `multiple` polls also merge a per-option `chosen` (the same selection again) and `ranked_choice` merges the per-option `rank`, but the option serializer itself only emits `{id, html, votes}`. Fixture at `fixtures/discourse/poll-vote-response.json`.
- `DELETE /polls/vote` - authenticated poll vote retraction with form fields `post_id`, `poll_name`, and `X-CSRF-Token`; allowed when the poll is open, the topic/post is still active, the user can post in the topic, and (if configured) the user belongs to the poll’s allowed groups. Discourse web UI also retracts on single-choice re-tap of the selected option. Its response body is `{ "poll": {...} }` with no `vote` key (the reader's selection is gone by definition).
- `GET /polls/voters.json?post_id={id}&poll_name={name}&option_id={option}&page={page}&limit={limit}` - public poll voter list. `option_id` is optional; pagination is independently partitioned per option, `page` starts at 1, and `limit` is clamped to 1..50. The response has no total/has-more field and omits an option key on an exhausted page, so the client uses the poll option's own vote count and page size to determine completion. Regular/multiple/ranked polls return an option map; number polls return a flat array and require a separate DTO path before native voter-list support. Fixture at `fixtures/discourse/poll-voters.json`.
- `GET /discourse-reactions/posts/{id}/reactions-users.json` - public reaction-user groups. Optional `reaction_value={id}` limits the response to one reaction. The current discourse-reactions controller does not support `offset`, `limit`, or a cursor and caps each returned group to its most recent 27 users while preserving the group-wide `count`; fixture at `fixtures/discourse/reaction-users.json`. Clients must not present the returned `users` array as a complete list when `count > users.size`.
- `GET /` - homepage HTML used for bootstrap parsing and WebView fallback
