## Assistant

我的建议：**纯 View，不要混 Compose**。理由结合你这个项目的实际情况：

**为什么不要混用**

1. **Telegram 的核心子系统天生反 Compose**。你的 AGENTS.md 把手势仲裁、动画曲线/插值器、自定义 Canvas 绘制、RecyclerListView 的 viewsByType 池都列为 *Forced Exact Component Port*。这些东西全是基于 View 的 `onTouchEvent / dispatchDraw / requestLayout / invalidate` 写的，搬到 Compose 等于推倒重写，直接违反 Exact Component Port 规则。

2. **手势会打架**。Compose 的 pointer input pipeline 和 Telegram 那套 `onInterceptTouchEvent + 自己算 velocity/slop/3000 阈值` 的逻辑嵌套时，边界事件会丢或重复（特别是横向 swipe + 竖向 scroll + 内嵌 WebView 这种）。Browser/InstantView/MediaViewer 这些重交互场景必踩。

3. **每个 ComposeView 都是独立的合成树 + 独立 input dispatcher + 独立 invalidate 链**，在 RecyclerView 的 cell 里反复创建/回收非常贵，而 Telegram 的列表性能恰恰来自极致的 View 复用。

4. **Theme 双轨制**。你已经在用 `Theme.getColor(Theme.key_*)`，再叠 MaterialTheme/CompositionLocal 等于两套 token 体系互相同步，长期就是 drift。

5. **现在目录结构 (`ui/actionbar`, `ui/photo`, `ui/mediaviewer`, `ui/components`) 就已经是纯 View 的 Telegram 形状**，没有历史包袱要照顾。

**什么时候可以破例（写进文档限制住）**

只在满足全部条件时才考虑局部 Compose：
- 是纯 NativeDo 业务面板（设置项列表、登录表单、空状态），不在 Forced Exact 子系统内；
- 不放进 RecyclerListView 的 cell 里；
- 不参与横滑/纵滑手势仲裁；
- 用 `AbstractComposeView` 包成一个独立的 leaf View，外部仍按 View 对待。

> 反向（Compose 里嵌 View）更糟：会让你的 ActionBar / Drawer / ViewPagerFixed 这些必须靠 Activity decor 和 View 层级配合的东西很别扭，直接排除。

**建议落到 AGENTS.md 的一条硬规则**

> UI 默认 100% View。Forced Exact Component Port 子系统（手势、动画、测量、Canvas 绘制、Recycler 池）禁止使用 Compose。`Native Feature` 类的静态面板如需 Compose，必须包成独立 `AbstractComposeView` leaf，且不得放入 RecyclerListView cell。
